# DuckDB Samples

A repository of samples that make DuckDB immediately relevant and approachable.

The samples are grouped into scenario folders:

| Folder | What it shows |
|---|---|
| [`odbc-scenarios`](odbc-scenarios) | Querying MySQL through the DuckDB **ODBC extension** with DuckDB embedded in a web app — the same demo built five times, once per language/framework. |
| [`batch-scenarios`](batch-scenarios) | Data transformation inside **Spring Batch** jobs — DuckDB's vectorized engine vs. looping over rows in in-memory Java collections. |
| [`wasm-scenarios`](wasm-scenarios) | A Java backend sends a dataset once and **DuckDB-Wasm** runs the SQL in the browser tab — including one where the backend produces the data with Python on GraalPy. |
| [`graalpy-scenarios`](graalpy-scenarios) | **DuckDB (JDBC) and Python (GraalPy) in one JVM** — DuckDB runs the SQL, Python applies the business rules, no boundary between them. |
| [`jsrs/jsr-381`](jsrs/jsr-381) | A **JSR 381** (Java Visual Recognition API) image classifier whose model is a **DuckDB table**: classifying is a nearest-neighbour vote in SQL. |

## odbc-scenarios: DuckDB ODBC vs. MySQL scanner in a web app

Query MySQL through the **DuckDB ODBC extension**, with DuckDB embedded in a web
app — built five times, once per language. See
[`odbc-scenarios`](odbc-scenarios) for details.

| Demo | Language | DuckDB binding |
|---|---|---|
| [`duckdb-odbc-java-demo`](odbc-scenarios/duckdb-odbc-java-demo) | Java (Spring Boot) | JDBC |
| [`duckdb-odbc-python-demo`](odbc-scenarios/duckdb-odbc-python-demo) | Python (FastAPI) | `duckdb` (PyPI) |
| [`duckdb-odbc-node-demo`](odbc-scenarios/duckdb-odbc-node-demo) | Node.js (Express) | `@duckdb/node-api` |
| [`duckdb-odbc-go-demo`](odbc-scenarios/duckdb-odbc-go-demo) | Go (net/http) | `duckdb-go` (cgo) |
| [`duckdb-odbc-rust-demo`](odbc-scenarios/duckdb-odbc-rust-demo) | Rust (Axum) | `duckdb` crate |

All five give **identical business results**; only JSON serialization differs.
The benchmark trio (100M `orders` rows) shows the data path dominates:

| Path | Time | What it does |
|---|---|---|
| ODBC extension | ~35–40 s | Streams every MySQL row over ODBC, then aggregates |
| MySQL scanner | ~12 s | Aggregates through DuckDB's native MySQL scanner |
| Native DuckDB | ~0.2 s | Aggregates a local DuckDB table — no round-trip |

The binding does not change performance; choosing the path is worth ~3× then
~60× again.

## batch-scenarios: DuckDB vs. Java loops in a Spring Batch job

Two Spring Boot + Spring Batch apps run the *same* transformation over the *same*
generated dataset — one looping over rows into an in-memory Java `HashMap`, the
other handing the aggregation to DuckDB's vectorized engine as one SQL statement.
See [`batch-scenarios`](batch-scenarios) for details.

| Demo | Transform step |
|---|---|
| [`spring-batch-java-demo`](batch-scenarios/spring-batch-java-demo) | Row-at-a-time loop into in-memory Java collections |
| [`spring-batch-duckdb-demo`](batch-scenarios/spring-batch-duckdb-demo) | One `COPY (SELECT … GROUP BY …)` on DuckDB's vectorized engine |

Both produce a **byte-identical** 8,000-group summary; only the transform time
differs (this machine, timing the transform step only):

| Rows | Java (in-memory collections) | DuckDB (vectorized) | Speedup |
|---|---|---|---|
| 10,000,000 | 1.00 s | 0.17 s | ~6× |
| 50,000,000 | 4.83 s | 0.61 s | ~8× |

The Java loop is single-threaded and pays per-row parsing/boxing costs; DuckDB
vectorizes the scan and aggregation across all cores — which is exactly why you'd
reach for it as the transformation step inside a batch job.

## wasm-scenarios: DuckDB-Wasm analytics in the browser, Java as the backend

A Java `HttpServer` serves a page and a CSV endpoint; the browser downloads the
CSV once and DuckDB-Wasm runs every aggregation and filter locally, as SQL. See
[`wasm-scenarios`](wasm-scenarios) for details.

| Demo | What it shows |
|---|---|
| [`duckdb-wasm-java-demo`](wasm-scenarios/duckdb-wasm-java-demo) | Two files — `Server.java` and `index.html` — with no Maven, npm or framework |
| [`duckdb-wasm-graalpy-demo`](wasm-scenarios/duckdb-wasm-graalpy-demo) | Same browser-side SQL, but the backend's data endpoint is generated by Python on **GraalPy** in the JVM |

Java only produces raw rows; the `GROUP BY`, `sum` and `avg` run in the browser
tab. The compute moves off the server, and because it is the same engine and the
same SQL as server-side DuckDB, a query written for one side runs unchanged on
the other. Best when a per-user dataset is small enough to download but gets
asked many questions; the trade-off is that the data has to fit in the tab and
the user can read everything sent.

The GraalPy variant shapes that dataset in Python, running in the same JVM as
the backend (the idea from `graalpy-scenarios` pointed the other way): Python
writes the rows, the browser's DuckDB-Wasm runs the SQL over them.

## graalpy-scenarios: DuckDB and Python in the same JVM

Following Graeme Rocher's PyCon FR 2026 talk [*Fusing Python with Java using
GraalPy and Micronaut*](https://www.pycon.fr/2026/en/talks/long-talk.html#talk-3JHBZY),
this runs Python inside the JVM so it sits next to a Java library — here DuckDB.
See [`graalpy-scenarios`](graalpy-scenarios) for details.

| Demo | What it shows |
|---|---|
| [`duckdb-graalpy-demo`](graalpy-scenarios/duckdb-graalpy-demo) | DuckDB (JDBC) aggregates 1,000 rows; Python (GraalPy) tiers and formats the result, in one process |

DuckDB does the vectorized SQL over the full dataset; Python applies the per-row
business rules to the small aggregated result. The rows pass from DuckDB into
Python as a Java array in the same process — no REST, no subprocess, no JSON.
DuckDB handles data volume, Python stays readable for the rules, and moving logic
between them is editing one file rather than crossing a network boundary.
