Open with the title and give it a moment. The idea: somewhere along the way we all accepted that transforming a few gigabytes of data means renting a distributed system by the second. This talk pushes back on that.

We rented a distributed system
to transform a few gigabytes.

Set up the problem. This is the everyday experience most people in the room will recognise.

Every dbt run is a round-trip you didn't need

  • Slow
  • Metered — you pay by the second
  • Queued behind your colleagues' CI jobs
Walk through the three costs of that round-trip: it's slow, you pay by the second, and you wait behind your colleagues' CI jobs. The last one tends to resonate most — everyone has queued on a shared warehouse.

If your whole project fits in
a few hundred GB…

…this is a strange way to live. You can stop.

State the main point plainly: a few hundred gigabytes fits on the laptop in front of you, so renting a cluster for it doesn't make sense — and you don't have to. Give it a short pause.

DuckDB

  • Free, MIT-licensed, in-process analytical database
  • No server. No account. No invoice.
  • Now in public beta on the dbt Fusion engine
Introduce DuckDB: free, MIT-licensed, and in-process, which means it runs inside dbt rather than over a network. It's now in public beta on the dbt Fusion engine, which is what makes this practical today.

What that unlocks

  • Sub-second model iteration on your laptop
  • Full-project CI in seconds on a plain GitHub runner
  • Python models that run in-process — your data never moves
Cover the three things this gives you: fast model iteration on your laptop, CI that runs in seconds on a plain GitHub runner, and Python models that run in-process so your data never leaves. The Python point is easy to miss, so call it out.

The warehouse becomes optional — at every stage

  • Native readers: Parquet, Iceberg, Postgres — read sources in place
  • DuckLake: publish your output tables in open formats
  • DuckDB-WASM: query them straight from the browser
  • Optional at every stage — not just development
Make the point that the warehouse is optional at every stage, not just development. DuckDB's native readers pull Parquet, Iceberg, and Postgres sources in place; DuckLake publishes your output tables in open formats; and DuckDB-WASM serves them in the browser. This leads into the demo.

Let's build one. Live.

Developed → Tested → Deployed → Served, entirely on DuckDB
~3M NYC taxi trips — more data than you'd think reasonable, on one laptop

Switch to the terminal and increase the font size. The warehouse is already gone, so you're genuinely starting from scratch and building the whole thing — developed, tested, deployed, and served — on DuckDB, over more data than people expect.

1 · Develop

$ dbt run
  • stg_trips — reads Parquet straight from a URL, no load step
  • payment_summary — a normal mart via ref()
  • trips_by_hour.py — a Python model, run in-process
Type `dbt run`. While it builds, explain what's happening: it reads about three million taxi trips straight from a Parquet URL, builds the models, and runs a Python model in the same process. It finishes in a few seconds.

2 · Test

$ dbt test
  • Schema tests: not_null, unique, accepted_values
  • One business assertion, over ~3M rows:
  • Credit-card riders tip $4.17 (28.7%). Cash riders: $0.00.
Type `dbt test`. Everything passes. The custom test checks, across all the rows, that credit-card riders tip more than cash riders — cash tips mostly go unrecorded. It's a genuine result, checked against millions of rows in under a second.

3 · Deploy

$ # the publish models wrote open Parquet during `dbt run`
  • publish_* models are materialized as external Parquet
  • Your output tables, in an open format — no warehouse to load
  • DuckLake does exactly this at production scale
Show the files in web/. Deploying here didn't mean loading a warehouse; it meant writing open Parquet files. DuckLake is the managed, production version of the same idea.

4 · Serve

$ cd web && python3 -m http.server 8000
  • Open http://localhost:8000
  • DuckDB-WASM queries the published Parquet in the browser
  • No backend. No server. The page IS the database.
Open the browser tab. The page runs DuckDB compiled to WebAssembly and queries the Parquet locally. Point out the tip numbers — the same results, now served from the browser with no backend.

The receipts

  • ~3,000,000 rows
  • Developed + tested in seconds — on this laptop
  • The DuckDB scan itself: milliseconds
  • Total cloud bill: $0.00
Go through the numbers: about three million rows, built and tested in seconds, the scan itself in milliseconds, and nothing on the cloud bill. The few seconds are mostly dbt starting up, so adding more data barely changes the time.

Your data is not that big.
